# AGENTS.md — ArchForge Project AI Context

## Project

ArchForge is a multi-repository project (AI Native Enterprise Application Platform).
This repository (`ArchForgeSpec`) is the project specification: machine-readable project map, architecture, API/Schema contracts, and AI context.

## Repositories

The project consists of five independent Git repositories, cloned side by side:

- `../ArchForge` — backend / core platform (Java 25, Spring Boot 4.1.0). Hosts two apps: `server-admin` (port 8080) and `server-web` (port 8081).
- `../ArchForgeWeb` — C-end web client (Next.js 15 + React 19).
- `../ArchForgeAdmin` — admin client (Vue 3.5 / vue-pure-admin).
- `../ArchForgeDocs` — documentation site (VitePress).
- `.` — project specification (this repository).

All repositories are fully independent Git repositories.
**Do not use Git submodules. Do not nest repositories.**

## Repository Relationship

- `ArchForge` is the backend platform and the sole API provider.
- `ArchForgeWeb` is an API consumer of `ArchForge` (`server-web`, port 8081).
- `ArchForgeAdmin` is an API consumer of `ArchForge` (`server-admin`, port 8080).
- `ArchForgeDocs` documents the whole project.
- `ArchForgeSpec` defines the shared contracts and architecture:
  - API contract: `api/openapi.yaml` (OpenAPI 3.1; authoritative spec generated by springdoc at `/v3/api-docs`)
  - Data / DSL schemas: `schemas/` (JSON Schema 2020-12)
  - Project manifest: `repos.yaml`
  - Architecture: `architecture.md`

## Local Workspace

Expected layout (siblings, flat):

```
archforge/
├── ArchForge/          # backend (server-admin :8080 + server-web :8081)
├── ArchForgeWeb/       # C-end web client
├── ArchForgeAdmin/     # admin client
├── ArchForgeDocs/      # documentation site
└── ArchForgeSpec/      # contracts / architecture / AI context (this repo)
```

If sibling repositories are missing, run:

```
./scripts/bootstrap.sh
```

To verify the workspace layout, run:

```
./scripts/check-workspace.sh
```

## Rules

Before changing cross-repository behavior:

1. Read `repos.yaml`.
2. Read the relevant architecture document (`architecture.md`) and, for in-depth
   guidance, the `ArchForgeDocs` site.
3. Inspect the affected repository.
4. Check API compatibility against `api/openapi.yaml` (and springdoc `/v3/api-docs`).
5. Do not modify another repository unless explicitly required.

Additional constraints:

- Never use Git submodules.
- Repositories are independent; relationships are described only by `repos.yaml`.
- Cross-repository contract is OpenAPI; UI/DSL contract is JSON Schema.
- Respect each repository's `can_modify` / `owns` boundaries in `repos.yaml`.
- Do not treat this repository as an SDK distribution; SDK generation is out of scope for now.
- Documentation belongs in `ArchForgeDocs`, not in `ArchForgeSpec`.
- **Contract sync rule**: when backend APIs change in `ArchForge`
  (server-admin / server-web), `api/openapi.yaml` must be updated in the same
  change. Keep this contract in sync with springdoc `/v3/api-docs`.
